# Personal AI — Phase 1 Database Design

**Status:** Implementation-ready proposal; decisions requiring product confirmation are listed at the end.  
**Database:** PostgreSQL 15+  
**Scope:** Seven tables only: `users`, `auth_sessions`, `providers`, `models`, `provider_configs`, `conversations`, and `messages`.

## 1. Goals and assumptions

This schema supports user accounts, login and refresh-token sessions, a catalog of AI providers and models, per-user provider credentials, conversations, and persisted messages. PostgreSQL is the source of truth. UUID primary keys are generated by the application or `gen_random_uuid()` (available in supported PostgreSQL versions).

The accepted architecture is:

- A provider has many models and independently has many provider configurations.
- A user owns provider configurations and conversations.
- A conversation uses exactly one model and one provider configuration at a time.
- A message belongs to one conversation; it stores its role, content, token count, and optional model reference.
- `models.context_window` describes a model capability; `messages.token_count` records observed usage for one message.
- Phase 1 does not include RAG, embeddings, memory, files, or tool-call tables.

Provider and model catalog rows are shared application catalog data; provider configurations are private to their owner. Model identifiers are provider API identifiers, not necessarily names shown in the UI. Values in examples are illustrative.

## 2. Relationship overview

```text
users 1 ──< auth_sessions
users 1 ──< provider_configs >── 1 providers 1 ──< models
users 1 ──< conversations >── 1 models
                         └──> 1 provider_configs
conversations 1 ──< messages >── 0..1 models
```

The schema uses composite foreign keys in `conversations` to ensure its selected model and provider configuration belong to the same provider. It also ensures the selected configuration belongs to that conversation's user.

## 3. PostgreSQL DDL

The following is a complete starting migration. Application code should generate UUIDs, timestamps, and token hashes using a cryptographically secure library. The DDL uses `pgcrypto` only for UUID generation; it does not encrypt secrets inside PostgreSQL.

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE users (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    email           text NOT NULL,
    display_name    text NOT NULL,
    password_hash   text NOT NULL,
    is_active       boolean NOT NULL DEFAULT true,
    email_verified_at timestamptz,
    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT users_email_nonempty CHECK (length(btrim(email)) > 0),
    CONSTRAINT users_display_name_nonempty CHECK (length(btrim(display_name)) > 0),
    CONSTRAINT users_password_hash_nonempty CHECK (length(password_hash) > 0)
);
CREATE UNIQUE INDEX users_email_ci_uq ON users (lower(email));

CREATE TABLE auth_sessions (
    id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id             uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    refresh_token_hash  bytea NOT NULL,
    issued_at           timestamptz NOT NULL DEFAULT now(),
    expires_at          timestamptz NOT NULL,
    revoked_at          timestamptz,
    last_used_at        timestamptz,
    replaced_by_id      uuid REFERENCES auth_sessions(id) ON DELETE SET NULL,
    user_agent          text,
    ip_address          inet,
    CONSTRAINT auth_sessions_expiry_after_issue CHECK (expires_at > issued_at),
    CONSTRAINT auth_sessions_revoked_after_issue CHECK (revoked_at IS NULL OR revoked_at >= issued_at),
    CONSTRAINT auth_sessions_last_used_after_issue CHECK (last_used_at IS NULL OR last_used_at >= issued_at),
    CONSTRAINT auth_sessions_token_hash_length CHECK (octet_length(refresh_token_hash) = 32),
    CONSTRAINT auth_sessions_user_id_id_uq UNIQUE (user_id, id)
);
CREATE UNIQUE INDEX auth_sessions_token_hash_uq ON auth_sessions (refresh_token_hash);
CREATE INDEX auth_sessions_user_active_idx ON auth_sessions (user_id, expires_at)
    WHERE revoked_at IS NULL;

CREATE TABLE providers (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    code            text NOT NULL UNIQUE,
    display_name    text NOT NULL,
    provider_type   text NOT NULL,
    base_url        text,
    is_active       boolean NOT NULL DEFAULT true,
    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT providers_code_format CHECK (code ~ '^[a-z0-9][a-z0-9_-]*$'),
    CONSTRAINT providers_name_nonempty CHECK (length(btrim(display_name)) > 0),
    CONSTRAINT providers_type_allowed CHECK (provider_type IN ('CLOUD', 'LOCAL', 'SELF_HOSTED')),
    CONSTRAINT providers_base_url_nonempty CHECK (base_url IS NULL OR length(btrim(base_url)) > 0),
    CONSTRAINT providers_id_code_uq UNIQUE (id, code)
);

CREATE TABLE models (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    provider_id     uuid NOT NULL REFERENCES providers(id) ON DELETE RESTRICT,
    model_name      text NOT NULL,
    display_name    text NOT NULL,
    context_window  integer NOT NULL,
    is_active       boolean NOT NULL DEFAULT true,
    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT models_name_nonempty CHECK (length(btrim(model_name)) > 0),
    CONSTRAINT models_display_name_nonempty CHECK (length(btrim(display_name)) > 0),
    CONSTRAINT models_context_window_positive CHECK (context_window > 0),
    CONSTRAINT models_provider_name_uq UNIQUE (provider_id, model_name),
    CONSTRAINT models_provider_id_id_uq UNIQUE (provider_id, id)
);
CREATE INDEX models_provider_active_idx ON models (provider_id, is_active);

CREATE TABLE provider_configs (
    id                      uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id                 uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    provider_id             uuid NOT NULL REFERENCES providers(id) ON DELETE RESTRICT,
    config_name             text NOT NULL,
    credential_ciphertext   bytea,
    credential_key_version  text,
    endpoint_url            text,
    is_active               boolean NOT NULL DEFAULT true,
    created_at              timestamptz NOT NULL DEFAULT now(),
    updated_at              timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT provider_configs_name_nonempty CHECK (length(btrim(config_name)) > 0),
    CONSTRAINT provider_configs_cipher_pair CHECK (
        (credential_ciphertext IS NULL AND credential_key_version IS NULL) OR
        (credential_ciphertext IS NOT NULL AND credential_key_version IS NOT NULL
          AND length(btrim(credential_key_version)) > 0)
    ),
    CONSTRAINT provider_configs_endpoint_nonempty CHECK (endpoint_url IS NULL OR length(btrim(endpoint_url)) > 0),
    CONSTRAINT provider_configs_user_id_id_uq UNIQUE (user_id, id),
    CONSTRAINT provider_configs_id_provider_uq UNIQUE (id, provider_id)
);
CREATE UNIQUE INDEX provider_configs_user_provider_name_uq
    ON provider_configs (user_id, provider_id, lower(config_name));
CREATE INDEX provider_configs_user_provider_active_idx
    ON provider_configs (user_id, provider_id, is_active);

CREATE TABLE conversations (
    id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id             uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    provider_id         uuid NOT NULL,
    title               text NOT NULL DEFAULT 'New conversation',
    model_id            uuid NOT NULL,
    provider_config_id  uuid NOT NULL,
    created_at          timestamptz NOT NULL DEFAULT now(),
    updated_at          timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT conversations_title_nonempty CHECK (length(btrim(title)) > 0),
    CONSTRAINT conversations_model_provider_fk FOREIGN KEY (provider_id, model_id)
        REFERENCES models(provider_id, id) ON DELETE RESTRICT,
    CONSTRAINT conversations_config_provider_fk FOREIGN KEY (provider_config_id, provider_id)
        REFERENCES provider_configs(id, provider_id) ON DELETE RESTRICT,
    CONSTRAINT conversations_config_owner_fk FOREIGN KEY (user_id, provider_config_id)
        REFERENCES provider_configs(user_id, id) ON DELETE RESTRICT
);
CREATE INDEX conversations_user_updated_idx ON conversations (user_id, updated_at DESC);
CREATE INDEX conversations_config_idx ON conversations (provider_config_id);

CREATE TABLE messages (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id uuid NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    role            text NOT NULL,
    content         text NOT NULL,
    token_count     integer,
    model_id        uuid REFERENCES models(id) ON DELETE RESTRICT,
    created_at      timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT messages_role_allowed CHECK (role IN ('SYSTEM', 'USER', 'ASSISTANT')),
    CONSTRAINT messages_content_nonempty CHECK (length(content) > 0),
    CONSTRAINT messages_token_count_nonnegative CHECK (token_count IS NULL OR token_count >= 0)
);
CREATE INDEX messages_conversation_created_idx ON messages (conversation_id, created_at, id);
CREATE INDEX messages_model_idx ON messages (model_id) WHERE model_id IS NOT NULL;
```

The first `conversations` sketch is shown to explain the desired constraint but is not executable. Use the second `conversations` definition in the actual migration. `provider_id` is therefore a required seventh-value key in that table, even though the conceptual relationship is that the conversation selects a model and config. It makes provider equality enforceable using ordinary foreign keys and avoids relying on application-only checks.

### Optional stricter message/model consistency

If every assistant message's `model_id` must match the conversation's selected model/provider, add `provider_id` to `messages` and a composite foreign key; otherwise enforce this rule in the transaction that inserts an assistant response. Keeping `model_id` nullable supports user/system messages and assistant messages where the model was not recorded. The basic schema above follows the requested shape and avoids another duplicated provider key.

## 4. Table and column reference

### `users`

Stores the account and login identity. One user can have many auth sessions, provider configurations, and conversations.

| Column | PostgreSQL type | Null/default | Purpose and checks |
|---|---|---|---|
| `id` | `uuid` | PK; generated UUID | Stable internal identity. |
| `email` | `text` | NOT NULL | Login identifier; trimmed nonempty and unique case-insensitively. Normalize consistently in the application. |
| `display_name` | `text` | NOT NULL | Name presented in the UI; nonempty after trimming. |
| `password_hash` | `text` | NOT NULL | Encoded result from Argon2id (preferred) or a suitably configured bcrypt/PBKDF2 implementation; never plaintext. |
| `is_active` | `boolean` | NOT NULL, `true` | Account access switch. |
| `email_verified_at` | `timestamptz` | NULL | Set when verification succeeds. |
| `created_at`, `updated_at` | `timestamptz` | NOT NULL, `now()` | Audit timestamps; update `updated_at` in application or trigger. |

### `auth_sessions` (authentication/JWT)

One row represents one refresh-token session/device, not each short-lived access JWT. Access tokens should be stateless and short-lived; store only a hash of each refresh token. A user has zero or many sessions. `replaced_by_id` supports token rotation lineage.

| Column | PostgreSQL type | Null/default | Purpose and checks |
|---|---|---|---|
| `id` | `uuid` | PK; generated UUID | Session identifier; can be used as JWT `jti`/session claim if desired. |
| `user_id` | `uuid` | NOT NULL, FK to users, cascade delete | Session owner. |
| `refresh_token_hash` | `bytea` | NOT NULL | 32-byte SHA-256 digest of a high-entropy random opaque refresh token; unique. Never save or log the raw token. |
| `issued_at` | `timestamptz` | NOT NULL, `now()` | Issuance time. |
| `expires_at` | `timestamptz` | NOT NULL | Must be after issue time. |
| `revoked_at` | `timestamptz` | NULL | Revocation time; null means not explicitly revoked. |
| `last_used_at` | `timestamptz` | NULL | Last successful refresh. |
| `replaced_by_id` | `uuid` | NULL, self-FK | New session/token after rotation; no cascading deletion. |
| `user_agent` | `text` | NULL | Optional device description; treat as untrusted personal data. |
| `ip_address` | `inet` | NULL | Optional last/initial IP; minimize retention and access. |

### `providers`

Catalog of provider services/runtimes (for example OpenAI, Google Gemini, Anthropic, Ollama). One provider has many models and many user-owned configs independently.

| Column | PostgreSQL type | Null/default | Purpose and checks |
|---|---|---|---|
| `id` | `uuid` | PK; generated UUID | Internal provider identity. |
| `code` | `text` | NOT NULL, unique | Stable machine key such as `openai`; lowercase pattern enforced. |
| `display_name` | `text` | NOT NULL | Human-readable provider name. |
| `provider_type` | `text` | NOT NULL | Restricted to `CLOUD`, `LOCAL`, `SELF_HOSTED`. |
| `base_url` | `text` | NULL | Catalog default endpoint; config may override. |
| `is_active` | `boolean` | NOT NULL, `true` | Whether new selections are allowed. |
| `created_at`, `updated_at` | `timestamptz` | NOT NULL, `now()` | Catalog timestamps. |

### `models`

Catalog of models made available by providers. `context_window` is the maximum input context capacity advertised for the stored model/version; it is not actual per-message token usage. A provider has many models; one model may be used in many conversations and messages.

| Column | PostgreSQL type | Null/default | Purpose and checks |
|---|---|---|---|
| `id` | `uuid` | PK; generated UUID | Internal model identity. |
| `provider_id` | `uuid` | NOT NULL, FK to providers, restrict delete | Owning provider. |
| `model_name` | `text` | NOT NULL | Exact API model identifier; unique within provider. |
| `display_name` | `text` | NOT NULL | UI name. |
| `context_window` | `integer` | NOT NULL | Positive token capacity. Keep configurable and refresh from trusted provider catalog data. |
| `is_active` | `boolean` | NOT NULL, `true` | Whether selectable for new conversations. |
| `created_at`, `updated_at` | `timestamptz` | NOT NULL, `now()` | Catalog timestamps. |

### `provider_configs`

Stores one user's connection configuration for one provider: a name, encrypted API credential, and optional endpoint override. A provider config belongs to exactly one user and one provider. Multiple configs for one provider are allowed per user, independently of model count.

| Column | PostgreSQL type | Null/default | Purpose and checks |
|---|---|---|---|
| `id` | `uuid` | PK; generated UUID | Config identity. |
| `user_id` | `uuid` | NOT NULL, FK to users, cascade delete | Owner. |
| `provider_id` | `uuid` | NOT NULL, FK to providers, restrict delete | Provider to which credential/settings apply. |
| `config_name` | `text` | NOT NULL | User label; case-insensitive unique per user/provider. |
| `credential_ciphertext` | `bytea` | NULL | Authenticated ciphertext (e.g. AES-256-GCM or envelope encryption); null is valid for local/no-key providers. |
| `credential_key_version` | `text` | NULL | Key identifier/version needed for decryption; must be present with ciphertext. |
| `endpoint_url` | `text` | NULL | Optional per-config endpoint. Validate scheme/host and block unsafe network destinations at application boundary. |
| `is_active` | `boolean` | NOT NULL, `true` | Disable without deleting credential/history. |
| `created_at`, `updated_at` | `timestamptz` | NOT NULL, `now()` | Audit timestamps. |

### `conversations`

Stores a user's chat and its selected model/config. Each row references one user, one model, and one provider config; the composite FKs guarantee both selected resources belong to the same provider and that the config belongs to the user.

| Column | PostgreSQL type | Null/default | Purpose and checks |
|---|---|---|---|
| `id` | `uuid` | PK; generated UUID | Conversation identity. |
| `user_id` | `uuid` | NOT NULL, FK to users, cascade delete | Owner. |
| `provider_id` | `uuid` | NOT NULL | Consistency key; must match both model and config provider via composite FKs. |
| `title` | `text` | NOT NULL, `New conversation` | User-visible title; nonempty after trimming. |
| `model_id` | `uuid` | NOT NULL, composite FK to models | Selected model. |
| `provider_config_id` | `uuid` | NOT NULL, composite FKs to provider_configs | Selected credential/settings. |
| `created_at`, `updated_at` | `timestamptz` | NOT NULL, `now()` | Creation and last activity/update timestamps. |

### `messages`

Stores ordered conversation entries. Phase 1 roles are `SYSTEM`, `USER`, and `ASSISTANT`, matching the prior design discussion. `token_count` is the measured token usage attributable to this message where available; it may be null when unknown. Provider usage is often reported for an entire request, so do not fabricate a per-message split: record prompt usage on the user message and completion usage on the assistant message only if the provider/application can measure them meaningfully. Otherwise leave null or adopt a future request-usage design.

| Column | PostgreSQL type | Null/default | Purpose and checks |
|---|---|---|---|
| `id` | `uuid` | PK; generated UUID | Message identity. |
| `conversation_id` | `uuid` | NOT NULL, FK to conversations, cascade delete | Parent chat. |
| `role` | `text` | NOT NULL | Restricted to `SYSTEM`, `USER`, `ASSISTANT`. Consider `text` plus CHECK for easier future role expansion. |
| `content` | `text` | NOT NULL | Plain text message body; empty string prohibited. |
| `token_count` | `integer` | NULL | Nonnegative measured token count; null means unknown/not available. |
| `model_id` | `uuid` | NULL, FK to models, restrict delete | Model that generated/was associated with this message; commonly set for assistant messages. |
| `created_at` | `timestamptz` | NOT NULL, `now()` | Message creation time; ordered with `id` as tie-breaker. |

## 5. Constraints, validation, and transaction rules

Database constraints enforce local invariants. The application must enforce rules involving external provider behavior and state transitions:

1. **Email:** trim and normalize on registration/update; database uniqueness uses `lower(email)`. A confirmation flow should not expose whether an account exists.
2. **Credential encryption:** encrypt before insert/update, decrypt only in the provider-call service, and never return ciphertext/plaintext to ordinary client endpoints.
3. **Conversation selection:** create/update a conversation only when the user owns the config, model is active, provider is active, config is active, and provider IDs match. Composite foreign keys enforce ownership and provider equality even if application checks fail.
4. **Messages:** insert messages under an authorized conversation in a transaction. An assistant message's `model_id`, if present, should match that conversation's selected model; enforce in application transaction or use an expanded composite-key design if strict database enforcement is required.
5. **Usage:** `token_count` must be nonnegative. Use `NULL` when unknown. `context_window` is a capacity, not a usage counter. Tokenization estimates may differ from billed provider usage.
6. **Timestamps:** update `updated_at` for changed users/providers/models/configs/conversations. A conversation's `updated_at` should advance when a message is added; do so in the same transaction.
7. **State changes:** revoke refresh sessions atomically during logout/rotation. On reuse of a rotated/revoked token, revoke the relevant session family and require reauthentication.
8. **Deletion:** user deletion cascades to that user's sessions, configs, and conversations/messages. Provider/model deletion is restricted when referenced so history cannot silently become orphaned. Prefer soft deactivation for catalog retirement.

## 6. Indexes

Indexes in the DDL cover email lookup, refresh-token lookup and active sessions, provider/model catalog lookup, per-user configuration names and provider filtering, conversation listing by recent activity, and chronological message retrieval. Add indexes only in response to query patterns. In particular, avoid a global index on message content until a search feature is designed; it can add storage and expose sensitive text through operational tooling.

## 7. Security and operational guidance

### Passwords

- Hash passwords with Argon2id using a maintained authentication library and a calibrated work factor. Store the complete encoded hash string, including parameters and salt, in `password_hash`.
- Never encrypt passwords for later recovery; never store plaintext, reversible passwords, or password hints.
- Keep authentication errors generic, rate-limit login and reset attempts, and use a separate secure password-reset flow.
- Restrict database access to the application role; exclude `password_hash` from normal user queries and logs.

### JWT and refresh tokens

- Use short-lived signed access JWTs. Validate signature, issuer, audience, expiry, and allowed algorithm. Do not put secrets or provider keys in JWT claims.
- Use high-entropy opaque refresh tokens, store only SHA-256 hashes (fast hashing is appropriate for randomly generated secrets), compare by hashing the presented token and using constant-time comparison where applicable.
- Rotate refresh tokens on use; revoke on logout, password change, or suspicious reuse. Expire sessions and clean up old rows on a scheduled retention policy.
- Protect tokens in transport and client storage. For browser clients, prefer `HttpOnly`, `Secure`, appropriately `SameSite` cookies with CSRF defenses as needed.
- `auth_sessions` is deliberately a refresh-session table. Do not persist every access JWT unless a later requirement calls for revocation/audit semantics that require it.

### Provider credentials

- Encrypt API keys before they reach the database using authenticated encryption; prefer envelope encryption backed by a managed KMS/secret store. Keep encryption keys outside PostgreSQL and outside source control.
- Bind ciphertext to context (for example config ID and user ID) as authenticated associated data. Store a key version, support rotation, and have a tested recovery/rotation process.
- Never log credentials, decrypted request headers, or full provider URLs if they can contain secrets. Expose only masked credential metadata in UI.
- Validate user-supplied endpoint URLs against SSRF risks: allow only approved schemes, block loopback/link-local/private ranges as appropriate, re-check DNS resolution, and set egress controls. Local/self-hosted provider use may need an explicit trusted-network policy.
- Use least-privilege database roles, TLS, backups with encryption, audit access to secret operations, and a retention/deletion policy.

### User data and authorization

Every query and mutation for `provider_configs`, `conversations`, and `messages` must be scoped by authenticated `user_id`. Do not assume that UUID secrecy is authorization. Consider row-level security later if it suits the deployment model, but keep application authorization mandatory.

## 9. Practical flows

### Register and authenticate

1. Normalize email and compute a password hash with the chosen password-hashing library.
2. Insert `users`; send verification through the authentication service if required.
3. After successful login, issue a short-lived access JWT and a random refresh token. Insert one `auth_sessions` row containing only the refresh-token hash and expiry.
4. On refresh, hash the presented token, locate the active unexpired session, revoke/rotate it, and insert the replacement session in a single transaction.

### Add a provider credential and start a chat

1. Select an active `providers` row and encrypt the submitted API key outside PostgreSQL.
2. Insert a `provider_configs` row owned by the current user.
3. Select an active `models` row for that provider.
4. Insert `conversations` with the user's ID, provider ID, model ID, and owned config ID. Composite foreign keys reject a cross-provider or another user's config.
5. When sending a prompt, authorize conversation ownership, load its model/config, decrypt the credential only in the provider adapter, and call the provider.
6. In a transaction, insert the USER and ASSISTANT messages, recording usage only when known, and update conversation activity. Store the assistant's model ID.

### Switch model/configuration

Update the conversation's `provider_id`, `model_id`, and `provider_config_id` together in one transaction. A model from another provider or config owned by another user fails the composite FK checks. Existing messages remain associated with their original per-message `model_id` where recorded.

## 10. Decisions to confirm

The schema makes explicit defaults so implementation can proceed, but confirm these product choices before stabilizing a production migration:

1. **Authentication approach:** Is Phase 1 email/password login with password reset and optional email verification, or an external identity provider/OAuth? If external-only, `password_hash` should become nullable and an identity table would normally be needed, which would change the seven-table scope.
2. **Meaning of the authentication table:** This document treats `auth_sessions` as refresh-token sessions; access JWTs are short-lived and not persisted. Confirm whether that is the intended interpretation of “authentication and JWT table.”
3. **Refresh-token form and lifetime:** Confirm opaque rotating refresh tokens and the expiry/idle timeout policy. `refresh_token_hash` assumes high-entropy opaque tokens, not self-contained JWT refresh tokens.
4. **Provider-config credentials:** Confirm which providers can be credential-free and whether one config may contain credentials/settings beyond one API key. The nullable encrypted secret supports local providers.
5. **Message token accounting:** Confirm whether the product needs prompt/completion token counts per message. This proposal stores one nullable `token_count`; exact request-level billing usually needs separate prompt/completion usage fields or a future usage table, which is outside the seven-table scope.
6. **System messages:** The agreed role set includes `SYSTEM`. Confirm whether system prompts should be persisted as conversation messages or supplied from server configuration.
7. **Conversation selection policy:** This design requires one current model/config pair on each conversation. If users should switch provider mid-conversation without changing a single current selection, messages can retain model IDs, but a per-turn config reference would require a schema change.
8. **Catalog ownership:** This assumes shared provider/model catalog rows managed by the application, with only credentials/configs user-owned.

## 11. Phase 1 boundary

Only the seven tables defined here are in Phase 1. Future retrieval-augmented generation, embeddings, long-term memory, tool executions, attachments, and detailed provider billing may require additional tables and migrations; they are intentionally excluded from this design.
